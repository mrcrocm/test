01

Cos'è Git e perché usarlo

Git è un sistema di controllo versione distribuito (DVCS) creato da Linus Torvalds nel 2005. Permette di registrare ogni modifica al codice sorgente nel tempo, tornare a versioni precedenti, collaborare con altri sviluppatori e tenere separate le sperimentazioni dalla versione stabile.

A differenza dei sistemi centralizzati, con Git ogni sviluppatore possiede una copia completa della storia del progetto sul proprio computer. Questo significa che puoi lavorare offline e che non esiste un unico punto di fallimento.

Concetto chiave Git non salva "differenze" tra file, ma snapshot dell'intero progetto ad ogni commit. Questo lo rende estremamente veloce nelle operazioni di confronto e navigazione della storia.

I tre stati di Git

Ogni file nel tuo progetto si trova sempre in uno di questi tre stati:

Working Directory
→
Staging Area
→
Repository

Working Directory è dove modifichi i file. Staging Area (o index) è dove prepari le modifiche da includere nel prossimo commit. Repository è il database permanente di tutti i commit.

git --version
Verifica la versione di Git installata sul sistema
git config --global user.name "Nome"
Imposta il nome che apparirà in ogni commit
git config --global user.email "email"
Imposta l'email associata ai tuoi commit
git config --list
Mostra tutte le impostazioni di configurazione attive
02

Controllare un Repository

Un repository (o "repo") è la cartella del progetto tracciata da Git. Contiene tutti i file del progetto più la directory nascosta .git/, dove Git conserva l'intera storia delle modifiche.

Creare o ottenere un repository

# Inizializza un nuovo repository nella cartella corrente
$ git init
Initialized empty Git repository in /progetto/.git/

# Oppure clona un repository esistente da remoto
$ git clone https://github.com/utente/repo.git
Cloning into 'repo'...

Controllare lo stato del repository

# Mostra lo stato di tutti i file (modificati, staged, untracked)
$ git status

# Versione compatta
$ git status -s

# Visualizza la storia dei commit
$ git log

# Storia compatta, una riga per commit
$ git log --oneline --graph --all

git clone <url>
Clona un repository remoto in locale con tutta la sua storia

git diff
Mostra le differenze tra i file modificati e l'ultimo commit
git show <commit>

03

Comandi Base

Il ciclo di lavoro quotidiano con Git ruota attorno a tre operazioni fondamentali: aggiungere modifiche all'area di staging, creare un commit, e inviare le modifiche al repository remoto.

Il ciclo add → commit → push

# 1. Aggiungi un file specifico allo staging
$ git add index.html

# 2. Aggiungi TUTTI i file modificati allo staging
$ git add .

# 3. Crea un commit con un messaggio descrittivo
$ git commit -m "feat: aggiunta pagina di contatto"

# 4. Invia i commit al repository remoto (es. GitHub)
$ git push origin main
Buona pratica — messaggi di commit Un buon messaggio di commit descrive cosa cambia e perché, non come. Usa l'imperativo: "Aggiunge login", "Corregge bug nel calcolo IVA". Molti team adottano la convenzione Conventional Commits (feat:, fix:, docs:...).

Annullare modifiche

# Rimuovi un file dallo staging (mantieni le modifiche nel file)
$ git restore --staged file.txt

# Scarta le modifiche nel working directory (IRREVERSIBILE)
$ git restore file.txt

# Modifica il messaggio dell'ultimo commit (prima del push)
$ git commit --amend -m "nuovo messaggio"
git add <file>

git add .

04

Comandi Utili

Oltre al ciclo base, Git offre strumenti potenti per navigare la storia, sincronizzare il lavoro con il team, rimuovere file e salvare temporaneamente il lavoro in corso.

Sincronizzazione con il remoto

# Scarica le modifiche dal remoto SENZA applicarle
$ git fetch origin

# Scarica E applica le modifiche (= fetch + merge)
$ git pull origin main

# Aggiungi un repository remoto
$ git remote add origin https://github.com/utente/repo.git

# Mostra i repository remoti configurati
$ git remote -v

Stash — salvataggio temporaneo

# Salva temporaneamente le modifiche non ancora committate
$ git stash

# Recupera le modifiche salvate
$ git stash pop

# Mostra la lista degli stash salvati
$ git stash list

Rimuovere file e reset

# Rimuovi un file dal progetto e dall'indice Git
$ git rm file.txt

# Smetti di tracciare un file ma mantienilo sul disco
$ git rm --cached file.txt

# Torna a un commit precedente (mantieni le modifiche)
$ git reset --soft HEAD~1

# Torna a un commit precedente (scarta tutto — ATTENZIONE)
$ git reset --hard HEAD~1
⚠ Attenzione git reset --hard scarta permanentemente le modifiche non committate. Prima di usarlo, considera git stash per metterle al sicuro.
git pull origin <branch>
Scarica e integra le modifiche dal repository remoto
git fetch origin
Scarica le modifiche senza applicarle al branch locale
git stash / git stash pop
Salva e ripristina modifiche temporanee senza committare
git rm <file>
Rimuove un file dal progetto e dal tracciamento Git
git reset --soft HEAD~1
Annulla l'ultimo commit mantenendo le modifiche in staging
git revert <commit>
Annulla un commit creando un nuovo commit inverso (sicuro)
05

Branching

Un branch è una linea di sviluppo indipendente. Lavorare su branch separati permette di sviluppare nuove funzionalità, correggere bug o fare esperimenti senza toccare il codice stabile del branch principale.

Il branch principale si chiama tradizionalmente main (o master nei repository più vecchi). Ogni nuovo branch parte da uno snapshot del branch da cui viene creato.

Gestire i branch

# Mostra tutti i branch locali
$ git branch

# Mostra tutti i branch (locali + remoti)
$ git branch -a

# Crea un nuovo branch
$ git branch feature/login

# Passa a un branch esistente
$ git checkout feature/login

# Crea un branch E spostati subito (forma breve consigliata)
$ git checkout -b feature/login

# Versione moderna con git switch
$ git switch -c feature/login

Rinominare ed eliminare branch

# Rinomina il branch corrente
$ git branch -m nuovo-nome

# Elimina un branch (solo se già mergiato)
$ git branch -d feature/login

# Elimina forzatamente un branch (anche se non mergiato)
$ git branch -D feature/login

# Pubblica un branch locale sul remoto
$ git push origin feature/login

git branch -m <nuovo>

06

Merging

Il merge integra le modifiche di un branch in un altro. Una volta completata una funzionalità sul suo branch, si fa il merge nel branch principale per includerla nel progetto.

Merge standard

# Spostati sul branch di destinazione (es. main)
$ git checkout main

# Integra le modifiche dal branch feature
$ git merge feature/login
Updating 3a8f1c2..9d4e7b1
Fast-forward
 login.html | 45 ++++++++++++++++++

Rebase — una storia più lineare

# Riapplica i commit del branch corrente sopra main
$ git rebase main

# Interrompi un rebase in caso di problemi
$ git rebase --abort
Merge vs Rebase Merge crea un commit di unione e conserva tutta la storia. Rebase riscrive la storia per renderla lineare. Usa il merge per branch condivisi, il rebase per pulizia di branch locali prima di fare merge.

Cherry-pick — prendere commit singoli

# Applica un singolo commit da un altro branch
$ git cherry-pick a1b2c3d
git merge <branch>
Integra un branch nel branch corrente creando un merge commit
git merge --no-ff <branch>
Forza un merge commit anche quando sarebbe possibile un fast-forward
git merge --squash <branch>
Comprime tutti i commit del branch in uno solo prima di integrare
git rebase <branch>
Riposiziona i commit del branch corrente sopra il branch indicato
git cherry-pick <hash>
Applica un commit specifico al branch corrente
git merge --abort
Annulla un merge in corso in caso di conflitti o errori
07

Conflitti

Un conflitto avviene quando due branch modificano la stessa parte dello stesso file in modo diverso. Git non può decidere autonomamente quale versione mantenere e richiede l'intervento dello sviluppatore.

Come appare un conflitto nel file

style.css — conflitto rilevato
<<<<<<< HEAD (tuo branch)
background-color: #0d1117;
======= (separatore)
background-color: #ffffff;
>>>>>>> feature/nuovo-tema (loro branch)

Devi modificare manualmente il file, scegliere quale versione tenere (o combinare entrambe), rimuovere i marcatori di conflitto (<<<<<<<, =======, >>>>>>>) e fare il commit.

Risoluzione passo per passo

# 1. Scopri quali file sono in conflitto
$ git status
both modified: style.css

# 2. Modifica il file manualmente e risolvi il conflitto
#    (usa un editor o uno strumento grafico)

# 3. Aggiungi il file risolto allo staging
$ git add style.css

# 4. Completa il merge con un commit
$ git commit -m "fix: risolto conflitto in style.css"

# Oppure, se vuoi annullare tutto e ricominciare
$ git merge --abort
Strumenti visivi per i conflitti VS Code, IntelliJ e altri editor moderni evidenziano i conflitti con pulsanti "Accept Current", "Accept Incoming", "Accept Both". Puoi anche usare git mergetool per aprire uno strumento di diff configurabile.

Prevenire i conflitti

Integra spesso le modifiche dal branch principale nel tuo branch (git pull frequente), tieni i branch di breve durata, e coordina con il team su chi modifica quale parte del codice.

git status
Identifica i file con conflitti da risolvere
git diff
Mostra in dettaglio tutte le differenze in conflitto
git add <file risolto>
Segna un conflitto come risolto aggiungendo il file allo staging
git merge --abort
Annulla completamente il merge e torna allo stato precedente
git mergetool
Apre lo strumento di merge configurato per risolvere i conflitti
git log --merge
Mostra i commit che hanno causato il conflitto
